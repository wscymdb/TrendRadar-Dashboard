# Git 提交与版本控制规范 (Git Rules)

在当前项目中执行 Git 提交或协助生成 Commit Message 时，必须严格遵循以下精简规范：

---

## 1. 提交信息结构 (Commit Format)

所有 Commit Message 必须遵循以下两段式结构（概述 + 空行 + 简要详情）：

```text
<type>: <精炼概述 (不超过 50 字)>

- 具体改动点 1 (简明扼要)
- 具体改动点 2 (非必需，不要太冗长)
```

---

## 2. 常用 Type 类型前缀

| 前缀 | 适用场景 | 示例 |
| :--- | :--- | :--- |
| **`feat:`** | 新增功能 / 新页面 / 新 API | `feat: 新增前端控制台配置面板` |
| **`fix:`** | 修复 Bug / 异常处理 | `fix: 修复 Docker 端口映射未暴露问题` |
| **`docs:`** | 文档更新 (README / 规则说明) | `docs: 更新部署与本地开发指南` |
| **`refactor:`** | 代码重构 (不影响功能的逻辑优化) | `refactor: 抽离 API 请求至独立模块` |
| **`style:`** | UI 样式微调 / 代码格式化 (不改变逻辑) | `style: 优化控制台卡片间距与排版` |
| **`chore:`** | 构建配置、依赖包更新、辅助脚本修改 | `chore: 更新 deploy.sh 与 .gitignore` |
| **`perf:`** | 性能提升与加载速度优化 | `perf: 优化热搜数据抓取缓存策略` |

---

## 3. 编写原则

1. **第一行精简**：`<type>: <简明描述>`，中文动宾结构，不要带句号。
2. **第二航空行**：必须留一个空行隔开标题与正文。
3. **正文克制**：使用 1~3 条短列表概括关键变动，**不要堆砌大量冗余文字**。
4. **禁止泄露敏感信息**：严禁在 commit 中包含真实的 Token、密码或 `.env` 凭证。
